> big update. Each numbered plan in this directory is executed as its own
> branch/PR using superpowers:executing-plans (inline execution — the
> project owner's stated preference, 2026-08-31) rather than
> subagent-driven-development, regardless of what the individual plan files
> still recommend. Execute plans in the order below unless the dependency

**Goal:** Implement every item in `SPEC.md` — 51 bugs and 8 features — as 14
independently landable PRs.

**Spec:** `SPEC.md` (bug/feature IDs), companion UX rationale in `ROADMAP.md`.

## Global Constraints (apply to every plan)

- Every bugfix starts with a failing regression test.
- No `unwrap()` in production code; use `Fallible`, `?`, and `fail()`.
- All error messages are user-facing and clear.
- Reviews and performance are written in one transaction; undo voids, never deletes.
- Cloze positions are byte positions: `.bytes()`, never `.chars()`.
- Update `CHANGELOG.xml` per item.

## Shared interface: flash messages

Plan 01 introduces `src/flash.rs`. Plans 02, 10, 11, 12, and 14 consume it and
must NOT redefine it. Canonical API:

```rust
// src/flash.rs — shared by drill and serve servers
pub enum FlashKind { Success, Error }
pub struct Flash { pub kind: FlashKind, pub message: String }
impl Flash {
    pub fn success(message: impl Into<String>) -> Self;
    pub fn error(message: impl Into<String>) -> Self;
    /// Redirect carrying the flash as ?flash=<percent-encoded>&kind=<success|error>
    pub fn redirect(self, to: &str) -> axum::response::Redirect;
    /// Extract from request query params (one-shot; rendered once)
    pub fn from_query(query: &std::collections::HashMap<String, String>) -> Option<Flash>;
    /// Dismissible banner: div.flash.flash-success / div.flash.flash-error
    pub fn render(&self) -> maud::Markup;
}
```

## Progress tracking (multiple agents, multiple machines)

The plan files themselves are the progress ledger. Protocol:

1. **Before starting anything:** `git fetch --all --prune` and
   `gh pr list --repo overcuriousity/hashcards-web` and check the status
   list below on origin/master. A plan with an open branch/PR or in-progress
   mark is taken — pick another.
2. **Claim a plan** by marking it "in progress" in the status list below,
   committing that one-line change to master and pushing immediately. Then
   create the plan's branch.
3. **While working:** tick the plan document's `- [ ]` checkboxes as steps
   complete and include the plan-file update in the same commit as the code
   it describes. Progress is then visible from any machine by looking at the
   branch, and survives interrupted sessions — a resuming agent reads the
   checkboxes to find where to pick up.
4. **On merge:** mark the plan "merged (PR #N)" in the status list below on
   master. The merged plan file arrives on master with all boxes ticked.

## Batching into work sessions

14 plans do not need 14 sessions. Batches below group plans that are safe
and efficient to do back-to-back in one session — grouped by dependency
order and file overlap (doing overlapping plans in one session avoids
cross-branch rebases). Keep **one branch and one PR per plan** even when a
session produces several; review size is the point of the split.

| Batch | Plans (in order) | Why together | Prerequisites |
|-------|------------------|--------------|---------------|
| A | 01 flash → 02 data-integrity | 02 depends on 01's `src/flash.rs`; both rework `drill/post.rs` — base 02's branch on 01's if 01 isn't merged yet | none |
| B | 03 parser-correctness → 04 parser-features | same files (`parser.rs`); 04 written assuming 03's changes | none |
| C | 05 rendering-safety + 06 security + 09 scheduling | three small, mutually disjoint plans; pure filler, can run anytime, also fine split across idle moments | none |
| D | 07 panic-hygiene + 08 database | 08 is self-contained (`db.rs`/`schema.sql`); 07 is a mechanical sweep best done after A is merged so handler churn has settled | A merged (for 07) |
| E | 10 edit-git + 11 hedgedoc | both serve-side flash consumers, disjoint from each other; 10 also wants B merged (plan 03 touches `edit.rs`) | A merged; B merged preferred |
| F | 12 serve-misc + 14 drill-polish | both session-lifecycle work; 12's eviction and 14's interrupt/progress accounting touch neighboring state | A merged |
| G | 13 stats + 15 cloze-rehash | 13 needs 08's migrations and 01's stats-default handoff; 15 claims 08's next migration number and is otherwise independent | A + D merged |

Minimum realistic session count: **7** (A–G). Batches B and C can run in
parallel with A on different machines from day one; D–G fan out once A is
merged. A single very long session could fold G into D (run 08 first, then
13) if A is already on master.

## Resolved: BUG-27 (decided 2026-08-31)

BUG-27 was omitted from the spec's own PR grouping, and its "minimal,
non-breaking" fix (u64 big-endian offsets) would in fact rehash every cloze
card on little-endian machines. The project owner ruled that rehashing and
migration are acceptable, so the full offset-independent rehash is planned as
**plan 15** (`2026-08-31-15-cloze-rehash.md`): the cloze hash input becomes
deletion *content* plus occurrence index (no byte offsets, no endianness or
pointer-width dependence), with a load-time migration that re-links existing
reviews/performance/bookmarks by recomputing each parsed card's legacy hash.
Depends on plan 08 (claims migration number 6).
